# v0.3 vs v0.4 流程对比：以"前后端图书管理系统"为例

> 需求示例：实现一个图书管理系统
>
> - **后端**：Node.js + Express + SQLite，提供 `GET /books`、`POST /borrow`、`POST /return` 三个接口，含库存边界校验（借出数量 > 库存时报 400）
> - **前端**：Vue 3 页面，图书列表 + 借阅/归还按钮 + 错误提示
> - **验收标准**：后端 `npm test` 全绿（含边界用例）；前端 `npm run build` 成功；联调用例通过

---

## 一、v0.3 流程：主模型当循环控制器（每步都是 LLM 决策）

```
┌─────────────────────────────────────────────────────────────────────┐
│ 主模型（LLM Orchestrator）—— 全程在线，每一步都要它思考和搬运          │
└─────────────────────────────────────────────────────────────────────┘

  需求（图书管理系统）
        │
        ▼
  ① 主模型拆解：后端任务 / 前端任务 / 联调，逐个手动组织任务文本
        │
        ▼
  ② delegate_task(worker=codex, "实现后端三个接口...")
        │
        │  ← 主模型阻塞等待，期间烧着上下文
        ▼
  ③ 读结果 → 主模型自己判断"后端做完了吗？"（自由发挥，无客观闸门）
        │
        ▼
  ④ delegate_task(worker, "实现前端列表页...")   ← 前后端只能串行等
        │
        ▼
  ⑤ 主模型手工搬运后端接口约定 → 塞进前端任务文本（转述可能失真）
        │
        ▼
  ⑥ review_changes(reviewer=opencode, "评审后端代码")
        │
        ▼
  ⑦ 读 verdict：FAIL？→ 主模型人工解析 findings
        │
        ▼
  ⑧ 主模型手工把 findings 复述进 continue_task → worker 返工
        │
        ▼
  ⑨ 再手动派一个新 reviewer 复审 → 再读 verdict → 再判断...
        │            （循环几轮全靠主模型盯着，烧 token 且判断标准不固定）
        ▼
  ⑩ 前端同样再来一遍 ⑥-⑨
        │
        ▼
  ⑪ 主模型自己拼"联调用例"，手动验证前后端拼起来能不能跑
        │
        ▼
  完成（主模型全程参与约 11 个决策点，每步都可能走偏且无兜底）
```

**v0.3 的痛点在这个例子里**：

- 前后端明明文件集互斥可并行，却只能主模型串行盯着
- findings 搬运靠主模型复述，转述失真无人发现
- "做完了没有"靠主模型读输出猜，worker 说测过就是测过
- 任何一步 vendor 卡死/抽风，主模型上下文里全是垃圾输出

## 二、v0.4 流程：状态机当控制器（主模型只出现在首尾）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 主模型只做两件事：开头写 WorkflowSpec，结尾看终态。中间零介入。          │
└──────────────────────────────────────────────────────────────────────┘

  需求（图书管理系统）
        │
        ▼
  ① 主模型写 WorkflowSpec（一次性）：
     ┌────────────────────────────────────────────────────────┐
     │ stage 1: backend  (worker)                             │
     │   acceptance: npm test        ← exit 0 才放行          │
     │ stage 2: frontend (worker, parallelGroups 可并行)      │
     │   acceptance: npm run build                            │
     │ stage 3: review   (reviewer, contextSessionIds:"upstream")│
     │   policy: maxReworkRounds=3, escalateOn="any"          │
     └────────────────────────────────────────────────────────┘
        │
        ▼
  ② run_workflow(spec) ──→ 立即返回 { workflowId }，主模型可以走开
        │
        ▼
╔════════════════════════════════════════════════════════════════════╗
║        AgentMesh 进程内状态机（确定性代码流转，零 LLM 参与）          ║
║                                                                    ║
║   ┌──────────┐      ┌──────────┐                                   ║
║   │ backend  │      │ frontend │   ← 文件集互斥，parallelGroups    ║
║   │ (worker) │      │ (worker) │     自动并行派发                   ║
║   └────┬─────┘      └────┬─────┘                                   ║
║        │                 │                                         ║
║        ▼                 ▼                                         ║
║   ┌─────────────────────┐                                          ║
║   │ acceptance 机器验收  │   npm test / npm run build 真实执行      ║
║   │ exit code 说了算     │   exit 1 ──→ escalated（见下方岔路）      ║
║   └──────────┬──────────┘                                          ║
║              ▼                                                     ║
║   ┌─────────────────────┐                                          ║
║   │ verify_contract_map │   worker 声称的 file:line 逐条机器核对    ║
║   │ （零 token 机械审计） │   对不上 ──→ 直接 FAIL                   ║
║   └──────────┬──────────┘                                          ║
║              ▼                                                     ║
║   ┌─────────────────────┐                                          ║
║   │ review (reviewer)   │   worker 产出经 contextSessionIds        ║
║   │ 只读 + 严格契约      │   "upstream" 一手注入，无人工转述         ║
║   └──────────┬──────────┘                                          ║
║              │                                                     ║
║        ┌─────┴─────┐                                               ║
║        ▼           ▼                                               ║
║      PASS        FAIL                                              ║
║        │           │                                               ║
║        │           ▼                                               ║
║        │   ┌──────────────────────────┐                            ║
║        │   │ findings 结构化落盘       │                            ║
║        │   │ → 自动注入原 worker 会话  │  ← 机器搬运，逐字无损       ║
║        │   │ → worker 返工 → 再复审    │    最多 3 轮（有界）        ║
║        │   └──────────┬───────────────┘                            ║
║        │              │ 轮次内修好→回到 review                      ║
║        │              │ 3 轮仍 FAIL ──→ escalated                   ║
║        ▼              ▼                                            ║
║   ┌─────────────────────┐                                          ║
║   │  终态 done          │                                          ║
║   └─────────────────────┘                                          ║
╚════════════════════════════════════════════════════════════════════╝
        │
        ▼
  ③ 主模型 get_workflow(workflowId, maxWaitMs=30000) 事件驱动长轮询
        │
        ├── done ──→ 收货。diff + 测试输出 = 交付证据
        │
        └── escalated ──→ 拿到完整证据链一次裁决：
              逐轮 findings + 验收命令 stdout/stderr + 仓库 diff 摘要
              （例：库存边界用例没写 → 验收失败 escalated，证据齐全）
```

**岔路兜底（以"worker 跑到一半 vendor 断了"为例）**：

```
  frontend stage: opencode 模型 10 分钟无输出
        │
        ▼
  看门狗标记 stalled ──→ 再 30 分钟无输出 ──→ 自动终止进程树
        │                                      │
        │                            终止前先溢出 checkpoint
        │                            （已产出的部分代码不丢）
        ▼
  policy.reRouteOnStall=true
        │
        ▼
  按健康度候选链换模型重派（3 连败的模型已被熔断隔离）
```

## 三、逐阶段对比表

| 阶段              | v0.3                                       | v0.4                                                             |
| ----------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| **拆解需求**      | 主模型逐个手动组织任务文本                 | 主模型写一份 WorkflowSpec，合同+验收一次固化                     |
| **前后端并行**    | 做不到，只能串行盯                         | `parallelGroups` 互斥文件集自动并行                              |
| **派发 worker**   | 每次手动 `delegate_task` 并等待            | 状态机自动派发（后台任务路径，registry/看门狗继承）              |
| **判断"做完了"**  | 主模型读输出自由发挥                       | `acceptance.commands` 真实执行，exit code 说了算                 |
| **接口约定传递**  | 主模型手工转述，可能失真                   | `contextSessionIds:"upstream"` 一手注入，逐字保留                |
| **评审**          | 手动 `review_changes`，读 verdict 自己判断 | 状态机触发，`verify_contract_map` 先零成本机械核对               |
| **findings 返工** | 主模型人工解析+复述+重派，轮数不固定       | 机器结构化注入，最多 3 轮，无 verdict 不放行                     |
| **vendor 断了**   | 主模型上下文被污染，人工收拾               | 看门狗终止 + checkpoint 保全 + 健康度换模型重派                  |
| **主模型介入点**  | 全程约 10+ 个决策点                        | 首尾 2 个（写 spec / 看 escalated）                              |
| **失败结局**      | 可能"看起来成功"                           | fail-closed：done / escalated / failed 三选一，绝不假成功        |
| **复盟能力**      | 翻聊天记录                                 | `metrics/health/findings/workflows.jsonl` 全程留痕，`stats` 聚合 |

---

## 四、一句话总结

- **v0.3**：主模型是工头，每块砖都要亲手搬、亲眼验、亲口传话——累、贵、且判断标准飘忽。
- **v0.4**：主模型是画图纸的建筑师——写完 spec 交班，施工（派发）、监理（验收+评审）、返工（findings 闭环）全是确定性状态机在跑，只有图纸本身有矛盾（escalated）时才被叫回来裁决。

## 五、执行过程中的异常情况清单及 v0.4 处理

> 标 ✅ = v0.4 真实压测已实证；标 ⚠️ = 已立案待修（P-075~P-078），均有文档化的手动缓解路径。
> 参考证据：`real_test_v0.4_report.md`、`PROBLEMS.md` P-075~P-078。

### 1. Vendor/模型层故障

| 情况                               | v0.4 的处理                                                                                                             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 模型输出卡死（生成中挂起）         | 输出流 10 分钟无新字节 → 标记 `stalled`；再 30 分钟 → 看门狗杀进程树，**先溢出 checkpoint 保住已有产出**，健康分扣分 ✅ |
| 模型反复报错（APIError 等）        | 失败计入 `health.jsonl`（24h 半衰期评分）；3 连败 → 熔断隔离拒派，返回预估冷却时间，到期自动恢复 ✅（T5：274s 冷却）    |
| 模型能力不匹配/拒绝任务            | 返回 `hint.nextCandidates` 升级链，按 tier→健康分→成本重派 ✅                                                           |
| 工作流中模型卡死                   | spec 开 `reRouteOnStall` → 按 M2 候选链**自动换健康模型重派**该 stage ✅                                                |
| 输出截断/半截 JSON                 | fake-vendor 仿真 harness 固化 8 类故障进 CI 回归 ✅；截断产出不进 finalAnswer，与诊断日志分离                           |
| vendor 真实错误被压成 UnknownError | ⚠️ **P-078 未修**：opencode 适配器压扁错误，目前靠 checkpoint + git diff 反推，已列 v0.5                                |

### 2. Worker 行为层

| 情况                       | v0.4 的处理                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 虚假声称"已完成/已测试"    | `verify_contract_map` 零 token 机械核对声称的 file:line；reviewer 抓行为不符（T7 抓出 critical 级虚假声称 ✅）                                   |
| 改验收测试凑通过           | 验收测试随 spec 下发 worker 无权改；`testFilesModified` 逐个审正当性，改测试 = FAIL ✅                                                           |
| 越界改动/删无关文件        | working-tree 变更检测 + `rollback_task` 回滚到派发前锚点重派                                                                                     |
| 遇 SPEC 矛盾静默选边       | 合同预写裁决规则 + reviewer 检查"声称与行为不符"（T7 实证抓出 ✅）                                                                               |
| 执行超时                   | 默认 10 分钟超时（可配至 1h），超时走 checkpoint 溢出 + 终止                                                                                     |
| rework 轮 vendor turn 失败 | ⚠️ **P-077 未修**：闭环断裂不自动重试；手动续跑 = 先看 git diff 判断死前状态 → 已落盘就重派复审 / 没落盘就 `continue_task + fromCheckpoint` 续跑 |

### 3. 调度/生命周期层

| 情况                | v0.4 的处理                                                                          |
| ------------------- | ------------------------------------------------------------------------------------ |
| 并发超过上限        | 新任务排队，`queued` 状态可见（带队列位置），事件驱动唤醒 ✅（T3）                   |
| 依赖任务失败/取消   | 下游标 `blocked`/`DEP_FAILED`，**不启动 vendor 进程**不烧配额 ✅（T3：DAG 级联取消） |
| 要中途取消          | `cancel_task`：幂等、结构化 NOT_FOUND/NOT_CANCELLABLE、先 checkpoint 后终态 ✅（T4） |
| 要暂停后再继续      | `pause_task` → checkpoint → `continue_task` 同会话续跑 ✅（T4）                      |
| 宿主/MCP 客户端断连 | AbortSignal 贯穿进程树，记 `client_disconnect` 失败终态，不误触发 fallback           |
| 守护进程重启留孤儿  | 启动扫描分类处理：死主收割、已完成释放、他人活跃任务 24h GC 宽限                     |
| 孤儿/僵尸进程残留   | 派发即脱离进独立进程组，终止时组级 SIGTERM→SIGKILL（Windows `taskkill /T /F`）✅     |

### 4. 评审层

| 情况                        | v0.4 的处理                                                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| reviewer FAIL               | findings 结构化落盘（category/kind/severity/file/line）→ 自动注入 worker rework ≤3 轮 → 复审 ✅（T7）                                 |
| reviewer 输出无 verdict     | fail-closed：UNKNOWN **不放行**，视为未通过                                                                                           |
| reviewer 自己卡死           | ⚠️ **P-075**：简报含命令指涉会致 opencode exit 124（双模型复现）；有效缓解 = 简报显式写"只读、禁止运行命令"；watchdog 正确记 stall ✅ |
| 评审含 SECURITY/SAFETY 警告 | 澄清前不接受 PASS，先核实是否误报                                                                                                     |

### 5. 上下文交接层

| 情况               | v0.4 的处理                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 上游产出传下游失真 | `contextSessionIds` 一手注入，禁人工转述；`handoff_diff` 机器判级（lossless→lost 五档，逐节审计）✅（T6：3/3 答对） |
| 上游仓库已变化     | freshness 标 `STALE`，下游明确知道哪些来源需重验 ⚠️（P-076：.agentmesh 运行时文件误触 STALE，待修）                 |
| 上下文超预算       | 24k 总预算分段限额，超限显式标 `[truncated]`，不静默丢                                                              |

### 6. 数据/资源层

| 情况                 | v0.4 的处理                                                                             |
| -------------------- | --------------------------------------------------------------------------------------- |
| JSONL 数据文件被写坏 | 损坏行跳过（fail-closed），stderr 明示，统计照常出 ✅（T8：注入垃圾行后 exit 0）        |
| 写盘途中崩溃         | 统一 StorageService 原子写：temp + fsync + rename                                       |
| 会话无限膨胀         | 50 turns/会话、200 会话 LRU 上限                                                        |
| token 超预算         | 水位门：80% 警告，达上限按策略 `rejectNew` 快速失败（BUDGET_EXHAUSTED），不中断在跑任务 |
| 坏模型继续被选中     | 健康分排序 + 熔断隔离，从候选链剔除                                                     |

### 汇总

28 种情况里，24 种有确定性处理且多数经真实压测实证；4 种已立案待修（P-075 / P-076 / P-077 / P-078）。共同模式：**每一个"处理"都是确定性行为（exit code / 结构化错误码 / 状态机转移），没有任何一条依赖"某个 LLM 觉得应该怎么办"。**
